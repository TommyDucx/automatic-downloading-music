第 01 课逆向工程是什么

假设你拿到一个玩具小车，一按遥控器它就跑。你想知道它里面是怎么做到的。两种办法： 一是去要设计图纸（如果厂家给你）——这叫看源码；二是把它拆开，看电机、齿轮、电路板怎么连—— 这叫逆向工程（Reverse Engineering）。

类比

逆向工程就像吃到一道好菜，倒推出菜谱。厨师不给你菜谱，你只能靠尝、靠看、靠试： 这味道像八角，火候大概三分钟，糖放得不多。你倒推出来的菜谱未必和厨师的一模一样， 但能做出一盘很像的菜，这就是目的。

放到软件世界里，逆向工程的定义是：在不给你源代码和文档的前提下，只根据「现象」， 反推出它内部的工作原理。

「现象」可以有很多种：

  • 一个能跑的网页——你能看到它发出的网络请求；
  • 一个能听的音乐 App——你能看到它请求了哪些网址；
  • 一个能玩的游戏——你能看到它的内存里有什么数字；
  • 一个可执行文件（.exe、.app）——你能看到它的机器指令。

最重要的一句话

记住

逆向的产物是「理解」，不是「破解」。理解之后，你可以自己写一个能用的脚本； 而「破解」通常意味着破坏别人的保护、绕过付费。这两件事在技术上相邻，在性质上完全不同。

我们这个项目为什么需要逆向？因为想要批量下载音乐并写入正确的专辑、封面、歌词， 就需要一个「能稳定调用的接口」。而很多音乐站点并不提供公开接口。 于是只能去看它的网页是怎么拿到歌的，然后照着那个方式，自己搭一条能走的路。

逆向能分成几个「地域」

不同目标的难度天差地别，入门阶段先认清这张地图：

目标类型你怎么观察它
网页 / 网络接口打开浏览器开发者工具，看 Network 面板里的请求。入门从这里开始
手机 App 的接口抓包（手机流量代理到电脑），一样是看请求
JavaScript 程序把代码下载下来直接读；读不懂就让它跑起来看
可执行文件 / 二进制需要反汇编器（Hopper、Ghidra、IDA），难度陡增

本课全程只讲第一类——网页与网络接口的逆向。它门槛最低、见效最快，也覆盖了本项目 90% 的工作。

第 02 课三观：动手之前先划边界

这一课很短，但我把它放在最前面。技术能力越强，边界越重要。

做法判断
自己学习、研究协议原理可以。这是技术知识的正常获取
访问公开可见的数据（你自己在浏览器里也能看到）可以，但要控制频率，别把人家的服务器打崩
下载内容仅供自己本地听 / 看属于个人使用范畴，但请遵守当地法律和平台条款
批量抓取后分发、上传、卖钱不可以。这是侵权，可能承担法律责任
绕过付费、把会员内容白嫖下来不可以。技术可行 ≠ 可以去做
攻击、篡改、影响他人服务不可以。可能构成违法
本项目自己定的三条红线

1. 不做任何登录态的逆向（不去破解 VIP）；
2. 只下载能公开访问的免费内容，且只供自己本地使用；
3. 主动限速（每次请求间隔 2～6 秒），不压垮对方服务器。

有意思的是：边界清楚反而让技术工作更好做。正因为不碰登录态，我们才能选一条 「不需要账号、不需要风控对抗」的简单路线——后面第 11 课会看到，这正是通关的关键。

第 03 课通用五步法

不管逆什么，套路是一样的。把它当成肌肉记忆背下来：

每一步的意思

  1. 观察：看到什么就记什么，不要先解释。比如「点了播放键，浏览器发出了一个请求， 网址里有一串 32 位的字符」。
  2. 假设：那 32 位大概是「签名」。假设可以错，但不能没有——没有假设的实验是瞎试。
  3. 实验：一次只改一个变量。改两个，你就不知道是哪个起了作用。
  4. 定论：能反复复现才算结论。只成功过一次的，叫「巧合」。
  5. 回写：写进文档。不回写等于没做——三天后你自己也想不起来当时怎么试出来的。
类比

这就是理科实验课的那一套：观察现象 → 提出假设 → 控制变量 → 得出结论 → 写实验报告。 你在物理课上学过的能力，直接就能用。

新手最常见的错误

跳过「假设」，直接开始乱改参数。看到报错就换一个参数，改了二十次毫无进展。 正确姿势是：先想清楚「我猜它怎么判断的」，再设计一个能验证或推翻这个猜测的实验。

第 04 课看懂一次网络请求

网页逆向的全部素材，都在一次 HTTP 请求里。先把它的结构认全。用 curl（一个命令行工具，macOS 自带）就能看清楚：

# 模拟浏览器访问酷狗的搜索接口，看看服务器返回什么
curl -s -A "Mozilla/5.0" \
  "https://complexsearch.kugou.com/v2/search/song?keyword=%E6%99%B4%E5%A4%A9&page=1&pagesize=3&platform=WebFilter"

把这条命令拆开，就是一次请求的全部构成：

部分长什么样作用
域名 / 路径complexsearch.kugou.com/v2/search/song 找谁、办什么事
查询参数?keyword=晴天&page=1 你的具体要求
请求头 HeaderUser-Agent: Mozilla/5.0… 你是谁、用什么身份来的
响应体一段 JSON 服务器的回答
类比

把它想成点外卖：
域名路径 = 店名 + 你要的服务（下单）；
查询参数 = 你要一份不加辣的牛肉面；
请求头 = 你的会员卡、手机型号、备注；
响应 = 店家回你「已下单，预计 30 分钟」。

练习：怎么看到这些

  1. 打开 Chrome，按 F12 打开开发者工具，切到 Network（网络）面板；
  2. 勾上 Fetch/XHR 过滤，只看数据请求；
  3. 在网页上做一个操作（比如搜一首歌）；
  4. 列表里会多出请求。点开任意一条，看 Headers（请求头与参数）和 Response（响应内容）。

顺手右键那条请求 → Copy as cURL，你就能把这次请求原样重放。 这是逆向的第一个实用技巧：先能重复它，才能研究它。

记住

逆向网络接口 = 在浏览器里看它怎么发请求 → 想办法自己发一个一模一样的。 所有的难度都集中在「一模一样」这四个字上。

那么，为什么不能照抄？

如果你直接拿 Copy as cURL 的请求去重放，很多时候会失败。原因是请求里藏着一些 只在当时那一刻有效的东西。常见的有三类：

  • 签名——一串哈希，证明「这个请求是我的合法客户端发的」，会随时间变化；
  • 令牌 / Cookie——你的登录身份；
  • 指纹信息——你的设备和浏览器特征。

接下来三课，就依次攻这三样。先从最核心的签名开始。

第 05 课签名：服务器的门禁暗号

为什么要有签名

服务器面对的是全世界。它需要快速判断：「这个请求是我们的客户端发的，还是别人写的脚本？」 最省事的办法就是：约定一个暗号。

类比

想象一个秘密俱乐部，进门要报暗号。暗号不能是固定的一句话——那样被听一次就废了。 所以约定是：把今天日期 + 暗号本上的词，一起算出个结果报出来。 会员有暗号本，能算对；服务员（服务器）也有暗号本，能校验。

这里用到的数学工具叫哈希函数（最常见的是 MD5）。它有三个性质：

  • 同样的输入，永远得到同样的输出（所以能校验）；
  • 输入改一个字，输出面目全非（所以防篡改）；
  • 从输出推不回输入（所以泄露了也没关系）。

我们来亲眼看一下第二条：

md5("晴天")      = 0f9f8a5c…
md5("晴天 ")     = 3c1d77e2…   ← 只多了一个空格
md5("晴天a")     = b7a91f04…   ← 完全看不出关系

三种常见形态

形态算法逆向难度
裸哈希hash(参数) 最容易，但服务端也最容易被冒充，现实中少见
加盐哈希hash(盐 + 参数 + 盐) 需要「盐」这个秘密词。本项目酷狗就是这种，能离线复刻
混淆 / 改造哈希把算法本身魔改，再混淆代码 几乎不可能离线复刻。本项目 GD 音乐台是这种
类比「盐」

暗号里加一个只有你和店家知道的词。别人偷听到你报的暗号，也没法算出下一次该报什么—— 因为他不知道那个词。

签名通常长什么样

在请求的查询串里，它会是一个看起来「格格不入」的参数：

# 其它参数都是人能读懂的，只有这个是乱码——它就是签名
?keyword=晴天&page=1&pagesize=3&platform=WebFilter
  &clienttime=1789789360000
  &signature=8F3A21C4D9E07B65A1F24C8D3E90B7A2

找签名的第一步永远是：看哪个参数像哈希——32 位十六进制（MD5），或 8 位大写十六进制 （截断后的 MD5）。

第 06 课动手：亲手造一个签名

下面是一个真实的签名算法（酷狗网页版，本项目的实测结论）。规则是：

签名 = MD5( 盐 + 参数按字母排序拼成 "k=v" + 盐 ).toUpperCase()

# 盐（一个固定的秘密串）
盐 = NVPh5oo715z5DIWAeQlhMDsWXXQV4hwt

改一改下面的输入，看签名怎么变。这就是服务器能验证你的原因—— 它用同样的公式算一遍，对不上就拒绝。

实验：签名三明治生成器

参数会先按名字排序，再拼成一条字符串，最后被「盐」夹在中间算 MD5。

把 keyword 里的「晴天」改成「睛天」（偏旁不同），看签名变成什么样。

从实验里应该看出来的三件事

1. 顺序是排序决定的，不是你想怎么写就怎么写——差一个字符就全长错；
2. 没有「盐」就算不出来。盐藏在网页的 JavaScript 里，所以逆向的第一步往往是「找盐」；
3. 结果是可重复的。同样输入永远同样输出，这就是它能当门禁的原因。

第 07 课实战：从零推出一个标准签名

这一课用项目里真实发生过的一次排障当教材。它完美演示了「五步法」怎么用， 也演示了一个错误假设会让你浪费多少时间。

现象

我们要调酷狗的搜索接口。按照网上找到的开源实现，拼好参数、算好签名发过去， 服务器返回：

{ "status": 1, "error_code": 152, "error_msg": "Parameter Error" }

Parameter Error，参数错误。听起来像是我们某个参数写错了。

第一个错误假设（也是大多数人的第一反应）

「那就是参数写错了，我一个个试」——于是开始参数消融：把参数减到最少， 再一条条加回去，看错误码变不变。

# 只留最必要的
{keyword, page, pagesize}                     → 152
{keyword, page, pagesize, platform}           → 152
{…, iscorrection}                             → 152
{…, area_code}                                → 152
把全部参数都加上                                → 152

错误码纹丝不动。这说明：问题不在业务参数上。消融虽然没能解决问题， 但它干净地排除了一个方向——「排除法」也是实验的价值。

关键的一步：换一个维度观察

不要继续在参数上打转，而是问：如果签名本身根本不对，会是什么表现？ 于是做了一组对照实验——把签名整个删掉：

不带 signature 参数  → { "error_code": 20006, "error_msg": "err signature" }
带我们的签名        → { "error_code": 152, "error_msg": "Parameter Error" }
这个对比告诉了我们什么

你有没有去过那种要盖章的门？
· 不盖章 → 保安说「你没盖章」（20006）；
· 盖了章 → 保安不吭声了，但另一个窗口说「表格填错」（152）。
说明章是真的被认了——格式对了。问题出在别处。

于是把嫌疑范围收窄到两处：要么是盐不对，要么是这套客户端参数（appid / clientver）不对。 接着写一个矩阵脚本，一次跑完所有组合：

# 变体矩阵：一次跑完，不要一个个手试
appid=1005  clientver=20489  → 152
appid=1005  clientver=11430  → 152
appid=3116  clientver=11440  → 20006 err signature   ← 换了盐之后，章又不认了
…（共 12 组，全都不通）

结论

这套「安卓端」的签名方案已经整体失效了——盐值轮换了，不是我们拼错了。 继续在这条路上折腾，无论怎么改参数都不会通。

于是横向去找网页版的那一套：换一个盐、换一套参数，一次就通了。

这一课真正要记住的

错误码是路标，不是噪音。
· 20006 err signature = 门口就没进来（没带签名 / 格式不对）；
· 152 Parameter Error = 进来了，但签名值不对或平台参数不对；
· 看到 152 就去改业务参数，是方向性错误。

第 08 课实战：签名读不懂怎么办

上一课的签名是「标准 MD5 + 盐」，还能自己写出来。但本项目最主要的战场——GD 音乐台—— 情况完全不同：

  • 签名函数叫 crc32()，但它根本不是 CRC32，而是 MD5；
  • 而且这个 MD5 被魔改过：标准 MD5 里 md5("abc") 的结果是 900150983cd24fb0d6963f7d28e17f72，它的结果是 9ef90af686e68195b6f6d89b69d3c584；
  • 代码还用 jsjiami.com.v7 混淆过，变量名全是 _0x4f2a 这种。

如果你打算「读懂它、然后自己实现一遍」，这条路基本是死的。所以换思路。

核心思想：打不过就借

类比

对方说的话你听不懂，还有方言口音。你不需要学会他的方言， 你只需要把他本人请来当翻译——他张嘴，你记录。

这段混淆的代码本身就是可执行的 JavaScript。那我们为什么不直接让它跑起来， 然后调用它自己的函数呢？Node.js 里有个 vm 模块，可以创建一个隔离的 JavaScript 运行环境。把这段代码丢进去，它的函数就归我们用了。

技巧 A：把混淆文件丢进虚拟机

const vm = require("vm");

// 1. 给这段代码准备一个「像浏览器」的环境（shim = 垫片）
const ctx = {
  location: { hostname: "music.gdstudio.xyz" },   // 它要读域名
  mkPlayer: { version: "2026.09.16" },          // 它要读站点版本号
  XMLHttpRequest: class {                          // 它要发请求去拿服务器时间
    open(){} setRequestHeader(){}
    send(){ setTimeout(() => {
      this.readyState = 4;
      this.status = 200;
      this.responseText = String(Math.floor(Date.now()/1000));
      this.onreadystatechange && this.onreadystatechange();
    }, 0); }
  },
};
ctx.window = ctx; ctx.globalThis = ctx;

// 2. 让它跑起来
vm.createContext(ctx);
vm.runInContext(混淆代码, ctx);

// 3. 直接调用它自己的签名函数
const 签名 = ctx.crc32("Resonance");

注意三件事：我们没有理解它的算法，但拿到了正确的结果； 「垫片」的作用是补上浏览器环境里它依赖的东西； 而且它依赖什么，我们是通过报错一点点试出来的——这本身就是实验。

技巧 B：把混淆的字符串表解开

混淆代码里，所有字符串都被藏起来了，用 _0x2783(索引, 密钥) 这样的函数取用。 但这个解码函数是定义在顶层的——代码一跑，它就成了全局函数。 于是可以把它抓出来，把整张字符串表翻译成明文：

// 正则找出代码里所有 (0x1c8, '0Bf6') 形式的调用点
const 调用点 = [...混淆代码.matchAll(/\((0x[0-9a-f]+),\s*'([^']+)'\)/g)];

// 逐个调用它的解码函数
const 明文 = new Set(调用点.map(([, i, k]) => ctx._0x2783(i, k)));
// 466 个调用点 → 去重后还原出 285 条明文

技巧 C：把全局函数包一层，看它被谁调用

这是三个技巧里最有用的一个。不动它的代码，只是把它的函数包一层， 顺手把参数记录下来：

const 记录 = [];
const 原函数 = ctx.md5;
ctx.md5 = function () {
  记录.push([...arguments]);      // 谁调用了我？参数是什么？
  return 原函数.apply(this, arguments);
};

ctx.crc32("Resonance");
console.log(记录);
// → [ "178978936|music.gdstudio.xyz|20260916|Resonance" ]

一句话就把签名公式钉死了：

签名 = MD5( 时间戳前9位 | 域名 | 站点版本号 | 入参 ).slice(-8).toUpperCase()
这一课要记住的

读不懂代码时，不要硬读，让它跑给你看。三种姿势：
A 造个环境让它运行 → 直接用它的函数；
B 找它的解码器 → 把隐藏的字符串翻译出来；
C 包一层它的函数 → 看它被谁用什么参数调用。
C 的价值在于：得到的是运行时的事实，不是你的猜测。

顺带得到的工程结论

知道了公式，还有一个问题：站点升级后公式会变。所以最终的方案不是把公式写死， 而是每次运行时现场去下载它的 crc32.min.js，装进虚拟机算签名。 这样站点怎么改，我们都跟着走——这就是本项目 gd-signer.js 的全部内容。

第 09 课当它看的不是签名，而是「你是谁」

签名算对了，请求也可能照样被拒。因为服务器还有别的判断维度：

机制它在看什么打法
Cloudflare 等防护 你的 TLS 握手指纹、IP、浏览器行为。给你发一个「挑战页」，通关后才发通行证 必须用真实浏览器跑完挑战
设备指纹 设备号、MAC、屏幕参数等。用来识别「是不是同一台机器」 把身份参数固定下来并持久化复用
人机验证（风控） 访问频率、行为轨迹（鼠标轨迹、滚动）。异常就要求验证码 降低频率；或模拟真实行为

一个反直觉的发现

很多教程会教你：「把浏览器的 cf_clearance cookie 抠出来，喂给 curl 就能过。」 我们实测的结果是：不行，照样 403。原因是这张通行证和你的 IP、你的 TLS 指纹绑在一起， 换一个程序去用，等于换了一个人拿着别人的通行证进门，一眼就识破。

从浏览器抠出 cookie 给 curl          → 403  （绑 IP + TLS 指纹）
用 Node 的 fetch 直接请求              → 被拦  （TLS 指纹不像浏览器）
改用系统自带的 curl                    → 通过  （网络栈更「像正常客户端」）
真无头浏览器 --headless=new            → 通过  （2026-09 实测）

所以本项目的下载器里有一句看起来很怪的注释：HTTP 一律走系统 curl，不要用 Node 内置的 fetch。 这不是玄学，是因为两者的网络实现不同，指纹也不同。

类比

就像门卫不只是看你的证件，还看你的身高、口音、走路姿势。 你借了别人的证，但姿势不对，照样被拦。所以正解不是「搞到一张证」， 而是换一个门卫认得的身份进去。

第 10 课错误码是路标

逆向过程中你会收到大量错误。新手把它们当噪音、一个个乱试； 老手把错误码当地图，因为它直接告诉你「卡在哪一层」。

返回含义下一步该做什么
20006 err signature 没带签名，或格式不对检查是否漏传了签名字段
152 Parameter Error 签名值不对，或平台参数不对换盐值、换端（网页/安卓）
30020 + SSA-CODE 响应头 签名全对，撞上风控降低频率；或放弃这条路线
-32001 Session not found 会话过期（不是限流）重新建立会话后重试
status: 0 但 HTTP 200 请求成功、业务拒绝读 msg 字段，通常是权限或资源不存在
一个反复出现的陷阱

别只看 HTTP 状态码。上面有个例子：-32001 会话过期时， 服务器返回的不是 200。如果你只判断 status === 200，就会漏掉整类错误， 表现为「莫名其妙什么都不返回」。

小测：你能看懂这几个错误吗

点选你认为正确的答案。

第 11 课别死磕：横向换端

这是本项目最有价值的经验，没有之一。

类比

你要进一栋楼，正门锁了。新手的做法是：「我一定要打开这扇门」—— 研究锁芯、配钥匙，花三天。
老手的做法是：绕楼走一圈。结果发现有侧门、消防通道、还有一扇给送外卖的没锁。

同一个功能，服务商往往有好几套接口：给网页用的、给安卓 App 用的、 给旧版 App 用的、给小程序用的。它们的验证强度常常相差很大—— 因为老接口是为了兼容旧版本客户端而保留的，往往根本不验签名。

本项目在酷狗上实测出来的对照表：

接口结果
gateway.kugou.com（安卓端签名） 全部失败，恒返回 152
complexsearch.kugou.com（网页端签名） 可用
wwwapi.kugou.com/play/songinfo 失败，30020 风控
m.kugou.com/app/i/getSongInfo.php（移动端老接口） 可用，而且完全不需要签名
lyrics.kugou.com/v1/search 失败，返回 0 字节空响应
krcs.kugou.com/search（老接口） 可用，而且完全不需要签名

结论很清楚：通过的那两条，都是移动端的老域名，都不用签名。 与其花三天破签名，不如花十分钟把候选端点列出来批量探一遍。

怎么做才不累

不要「试一个、改一次、再试一个」。写一个矩阵脚本，把所有组合一次跑完， 输出只打三样东西：状态码、命中条数、第一条结果的标题。一眼就能看出哪一格是绿的。

# 变体矩阵的思路：把「猜测」变成「一次实验」
for 端点 of [正门, 侧门, 后门, 老门] {
  for 身份参数 of [dfid 的 4 种写法] {
    for 版本组合 of [appid × clientver 的 12 组] {
      打印(状态码, 命中条数, 首条标题)
    }
  }
}

还有一个「反向」的技巧

找不到参数该填什么时，去看别人的开源实现。本项目用的就是这条路： 先找到已有的开源项目（酷狗那边是 KuGouMusicApi）， 其中盐值、签名、参数全是明文写在 JavaScript 里的。

记住

先搜有没有现成的，再决定要不要自己逆。别人已经逆向过的东西， 你没有义务再逆向一遍。这也是搜索能力属于逆向能力的一部分的原因。

第 12 课证据分级：做一个诚实的逆向者

这一课讲的是「怎么把结论写下来」。它看起来像文科要求，实际上是工程要求—— 因为三个月后的你，会忘记当时是怎么得出结论的。

任何一条结论，都必须标注它是哪一级：

observed · 观测

我亲手跑出来过

inferred · 推断

我从别的现象推出来的

unknown · 未覆盖

我没测过，不知道

不诚实的写法诚实的写法
「这个接口支持无损。」 「实测：免费曲目（搜索结果里权限字段为 0）可下到真无损， 实测某首歌 32.8MB / 1061kbps，文件头魔数为 664c6143； VIP 曲目未覆盖，因为没做登录态。」
「签名算法是 MD5。」 「签名看起来是 MD5 结构（32 位十六进制），但实测它对 "abc" 算出的值与标准 MD5 不同，说明内核被改过 （推断：可能是换了常量或做了额外变换）。」

为什么要这么较真

  • 边界比结论更重要。「能下无损」+「仅限免费曲目」才是完整信息。 只说前半句，下次别人拿 VIP 歌去试，会被你坑一整天。
  • 脚本注释就是给人看的说明书。本项目每个下载脚本的头部都写着 「逆向来源」和「失效条件」，就是为了让接手的人知道它什么时候会坏。
  • 失效是常态，不是意外。站点会升级、盐会轮换。标了日期的结论， 失效时你只需要重新验证，不需要从零再来。

回写的标准模板

## 某接口可用性（YYYY-MM-DD 实测）

| 端点 | 签名 | 结果 |
|---|---|---|
| a.example.com/xxx | 无 | ✅ 可用 |
| b.example.com/xxx | MD5+盐 | ❌ 恒 152 |

- 实测证据：（贴命令与返回，注明是否复现过）
- 能力边界：（只在什么条件下有效、什么情况没测）
- 失效条件：（盐值轮换 / 端点下线 / 需登录）

还有一个「不要相信它说的话」的例子

接口返回的参数里有个 br（比特率），意思是「这首歌的音质」。听起来可以直接信， 但实测发现它经常虚标：

所以真正可靠的判断方式是：用文件大小 ÷ 时长反推实际码率，而不是相信它自称的数字。 这就是本项目的选源机制——把每个音源都扫一遍，按实际品质排序，再挑最好的那个下载。

记住

第 14 课踩坑集：我走过的弯路

这一节全部是真实的错误。看别人踩坑是最省学费的学习方式。

坑 1 · 把错误码当噪音

看到 152 Parameter Error，真的以为是自己参数拼错了，开始逐个试参数。 浪费了一整轮。真相是签名盐值已经轮换，跟参数毫无关系。

教训：先读错误码的语义，再动手。花两分钟理解 20006 / 152 / 30020 的区别， 能省一整晚。

坑 2 · 在一个维度上死磕

安卓端这条路已经死了，还在换 appid、换 clientver、换设备号—— 一共试了 12 组以上，全是 152。而正确答案是换到网页端，一次就通。

教训：连续三次同类型失败，就应该换维度，而不是换数值。

坑 3 · 拿「看起来相关」的东西当原因

搜索失败时，曾经以为是「被限流了」。后来发现真正原因是 曲名里带了半角括号或撇号——这类字符在参数编码时不会被转义，导致服务端算出的签名 和本地不一致。换成纯 ASCII 标题立刻正常。

教训：「限流」是最容易被滥用的解释。用对照实验验证： 同一时刻换一个干净的输入，如果通了，就不是限流。

坑 4 · 在没有必要的环境里硬撑

为了验证一个接口，尝试在沙箱里 npm install 把整个服务端装起来，结果进程被杀。 而实际上用纯 HTTP 请求就能验证，压根不需要跑那个服务。

教训：先问「验证这个结论，最少需要做什么」。能一条 curl 解决的， 别去装一整套环境。

坑 5 · 把「同名」当成「同一首歌」

歌词接口只按歌名检索，实测把《海阔天空》匹配到了一首翻唱版的歌词， 歌词第一行还带着「本歌曲翻唱由某某提供」的水印。

教训：名字匹配永远不可靠。加上时长校验（差超过 6 秒就丢弃）， 并且记牢一句话：宁可没有，也不要错的——错版本比没版本更糟。

坑 6 · 忘了回写

有些结论当时想明白了，没写下来，下次遇到同样的问题又debug了一遍。

教训：结论不落文档，等于没做。这也是这门课第 03 课第五步存在的唯一理由。

附 录 B下一步怎么练

看会了不等于会。按下面这个顺序练，两周就能独立干活。

第 1 周 · 观察力

  1. 打开任意网站的开发者工具 Network 面板，随便点几下，把每个请求的 四要素（域名路径 / 参数 / 请求头 / 响应）念出来；
  2. 找一条 GET 请求，右键 Copy as cURL，粘到终端运行—— 看你能不能复现浏览器看到的响应；
  3. 找一条带 signature 或 token 的请求， 试试把它删掉再发，看错误码怎么变。这是最有信息量的一步。

第 2 周 · 动手力

  1. 把本项目的 kugou-downloader.js 读一遍，对照本课第 06 课， 找到那个签名函数，验证它算出来的值和你手算的一样；
  2. 用 --probe 参数跑一次，看它打印的候选和档位，理解 「匹配分」是怎么打出来的；
  3. 读 gd-signer.js（只有 100 多行），对照第 08 课的技巧 A， 看清那三个 shim 各自解决什么问题。

第 3 周起 · 独立思考

挑一个你日常用的网站或 App，给自己出题：
「它搜索的时候发了什么请求？」→「有没有签名？」→「签名怎么算的？」→ 「能不能自己写个脚本复现？」

不要一上来就挑最难的。先从没有签名的公开接口练手， 建立起「我能看懂并复现」的信心，再逐级往上爬。

最后的建议

逆向工程真正难的不是技术，是纪律：
先观察再假设、一次只改一个变量、连续失败就换维度、 结论必须分级并写下来、动手之前先想清楚边界。
这五条做到了，你比 90% 只会复制粘贴脚本的人走得远得多。
